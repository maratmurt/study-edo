# День 04 — Сертификат X.509: поля, цепочка, отзыв

**Время:** 1,5–2,5 ч  
**Цель дня:** читать сертификат глазами саппорта и понимать, почему проверка «валидности» падает.

## Теория

### Что такое сертификат

**Сертификат X.509** — документ УЦ, который связывает:

- **идентичность** субъекта (ФИО, организация, ИНН и т.д.);
- с **открытым ключом**;
- на **срок действия**;
- с **ограничениями** использования (назначение ключа, политики).

Подпись УЦ на сертификате говорит: «мы удостоверили эту связь».

### Поля, которые спрашивают в поддержке

| Поле | Зачем |
|------|--------|
| **Subject (DN)** | Кто владелец: CN, O, INN, OGRN, SNILS… |
| **Issuer** | Кто выдал (промежуточный/корневой УЦ) |
| **Valid from / to** | Срок; «истёк» — частая причина отказа |
| **Serial number** | Идентификация при отзыве |
| **Key usage / Extended key usage** | Можно ли подписывать документы, клиентский TLS и т.д. |
| **Public key algorithm** | ГОСТ 2012-256/512 vs RSA |
| **SKI / AKI** | Связь с цепочкой издателей |
| **CRL Distribution Points / AIA** | Откуда брать отзыв и цепочку |

### Цепочка доверия

```text
Корневой УЦ (в доверенных)
    └── Промежуточный УЦ
            └── Сертификат пользователя
```

Проверка подписи документа включает:

1. криптопроверку подписи открытым ключом из сертификата подписанта;  
2. построение цепочки до доверенного корня;  
3. проверку сроков всех звеньев;  
4. проверку, что сертификат **не отозван** (CRL или OCSP).

Если корневой УЦ не установлен в хранилище доверенных — «подпись недействительна», хотя файл подписан правильно.

### CRL и OCSP

- **CRL** — список отозванных серийных номеров (файл, который обновляют).  
- **OCSP** — онлайн-запрос «отозван ли этот сертификат сейчас?».

Типичные сбои:

- нет доступа в интернет к CDP/OCSP с рабочей станции;  
- устаревший кэш CRL;  
- корпоративный прокси режет OCSP.

### OID

**OID** — числовой идентификатор алгоритма или расширения. В логах и ASN.1 встречаются строки вроде `1.2.643.7.1.1.1.1` (ГОСТ). Для саппорта достаточно уметь сопоставить «это ГОСТ, не RSA» через свойства сертификата в GUI.

## Практика

### Вариант A — Windows + сертификат

1. Откройте `certmgr.msc` (сертификаты текущего пользователя).  
2. Найдите любой личный сертификат (или тестовый КЭП).  
3. Выпишите в журнал:
   - Subject (CN, организация, ИНН если есть);
   - Issuer;
   - срок действия;
   - алгоритм ключа;
   - есть ли путь сертификации (вкладка «Путь сертификации») — сколько звеньев, все ли «ОК»;
   - назначение (вкладка «Состав» / Enhanced Key Usage).  
4. Ответьте: что будет, если удалить промежуточный УЦ из хранилища?

### Вариант B — только файл .cer / PEM

1. Откройте сертификат двойным щелчком или через `certutil -dump file.cer` (если доступен).  
2. Заполните ту же выписку полей.  
3. В журнале опишите сценарий: «пользователь экспортировал .cer коллеге — коллега может подписывать?» (ответ: нет).
