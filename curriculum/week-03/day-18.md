# День 18 — Проверка подписи и ловушка «ГОСТ vs RSA»

**Время:** 1,5–2,5 ч  
**Цель дня:** уметь проверить подпись и диагностировать несовпадение алгоритмов/инструментов.

## Теория

### Где проверяют подпись

| Место | Кто | Типичный инструмент |
|-------|-----|---------------------|
| Рабочее место | Пользователь/саппорт | КриптоПро, плагин, certmgr |
| Сервер приложения | Backend | КриптоПро CSP/JCP, криптосервис |
| Оператор ЭДО | Диадок | Своя проверка при приёме |
| Контрагент | Их контур | Их CSP/оператор |

«У меня открывается» ≠ «у проверяющего валидно».

### Алгоритмический контракт

Подписывающая сторона и проверяющая должны согласовать:

- алгоритм подписи (ГОСТ 34.10-2012-256/512 vs RSA);  
- алгоритм хеша;  
- формат (CAdES-BES/T, detached/attached);  
- необходимость цепочки сертификатов в CMS;  
- политику отзыва (online OCSP с сервера).

Классический тикет: фронт подписал **ГОСТ**, старый сервис проверки ждал **RSA/SHA-256** → «подпись неверна».

### Практическая проверка целостности

1. Есть исходные данные + detached-подпись.  
2. Проверяющий считает хеш тех же байтов.  
3. Проверяет криптоподпись.  
4. Строит цепочку и отзыв.

Изменение переноса строк, BOM, перекодировка UTF-8 ↔ Windows-1251 — частая причина «вчера было ок».

## Практика

### Вариант A

1. Возьмите подпись с дня 17 (или подпишите файл снова).  
2. Проверьте её инструментом КриптоПро.  
3. Измените 1 байт исходника → проверка должна упасть.  
4. В журнале опишите кейс для коллеги: «Фронт ГОСТ, сервис проверки RSA» — симптомы, как подтвердить (поля сертификата, OID), что делать (менять проверку или политику подписи).

### Вариант B

1. Заполните таблицу совместимости:

| Подпись | Проверка OpenSSL «из коробки» | Проверка КриптоПро | Проверка «старый Java без ГОСТ» |
|---------|-------------------------------|--------------------|----------------------------------|
| ГОСТ CAdES | | | |
| RSA PKCS#7 | | | |

2. Напишите мини-runbook «алгоритм не совпал» для L2.
